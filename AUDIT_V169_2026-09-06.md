## 1. Executive verdict

PRIV SPACA v169 has a strong feature set and several good production controls, but it should **not yet be described as security-hardened or enterprise-ready**. The audit found one critical authentication defect, multiple high-impact privacy/data-integrity defects, and several scalability and hardening gaps.

### Current level

- **Feature/product maturity:** 8.8/10 — polished commercial V1/V2
- **Production engineering:** 7.5/10 — good startup-production foundation
- **Security assurance:** 5.4/10 until P0/P1 findings are fixed
- **Overall audited readiness:** **7.1/10**
- **Recommended label:** production beta / controlled private community
- **Not yet:** high-assurance private messenger, regulated-data product, or hyperscale platform

## 3. Critical finding

### CRIT-01 — Passkey/biometric 2FA verification is bypassable

**Evidence:** `api/routes/auth.js:622-646`, `app.js:13315-13342`, `react-auth/main.jsx:168-184`.

The server catches WebAuthn verification/parsing errors and then treats any non-empty `signature` plus any non-empty `authenticatorData` as verified:

```js
catch (...) {
  verified = !!signature && !!authenticatorData;
}
```

The implementation also does not implement the WebAuthn assertion ceremony correctly:

- Clients use a new random challenge instead of the server challenge.
- `clientDataJSON` is not sent or verified.
- RP ID hash, origin, type, user-presence/user-verification flags and sign counter are not verified.
- The stored key is handled as if it were raw X/Y coordinates even though `getPublicKey()` normally returns SPKI/COSE-derived key data.
- Passkey registration accepts client-supplied credential/key data without a server registration challenge or attestation-response verification.
- Challenges live in an isolate-local Map, so legitimate verification can fail when requests land on different Cloudflare isolates.

**Impact:** anyone who has the password for an account with biometric 2FA enabled can bypass the second factor using malformed/non-empty assertion fields. The UI promise “biometric 2FA” is therefore not true server-side protection.

**Required fix:** disable the passkey toggle/routes immediately or replace the implementation with a standards-compliant WebAuthn library and durable one-time challenge storage. Fail closed on every parsing/verification error. Add negative tests proving malformed assertions, wrong origin, wrong challenge, replay and missing UV are rejected.

## 4. High findings

### HIGH-01 — All authenticated users receive other users’ email addresses

**Evidence:** `api/lib/helpers.js:171-180`; `/api/users`, follow-request events and multiple profile/post response paths call `sanitizeUser()`.

`sanitizeUser()` always includes `email`, even when `includePrivate` is false. Consequently, any authenticated member can enumerate email addresses through `/api/users` and other responses.

**Impact:** direct PII disclosure, phishing/account-correlation risk and violation of the app’s private positioning.

**Fix:** omit email by default; expose it only for the authenticated user’s own `/api/auth/me` or update response. Add an API contract test asserting that other users never contain `email`, DOB, push subscriptions, auth fields or recovery fields.

### HIGH-02 — Field-level encryption is defeated by the plaintext `ps_kv` mirror

**Evidence:** `api/lib/db.js` writes the decrypted whole database into `ps_kv`; `api/lib/store-turso.js:337-359` serializes it without `encryptUserPII()`.

Production secret configuration includes `FIELD_KEY`, but the audited database snapshot showed:

- `ps_kv` contained plaintext email fields for every user in that snapshot.
- `ps_kv` contained plaintext date-of-birth and push endpoint data where present.
- Structured `ps_users` still had 11 plaintext email rows, one plaintext DOB row and two plaintext push endpoints due incomplete dual-read migration.

No PII values were printed during the audit.

**Impact:** a database-only compromise still reveals the data the field encryption claims to protect. The plaintext mirror also contains the application’s full legacy data model.

**Fix:** stop storing decrypted user PII/push subscriptions in `ps_kv`, or encrypt every sensitive field before mirror serialization. Run an idempotent migration for all existing structured and mirror records. Add a database assertion that fails deployment if any plaintext protected field remains.

### HIGH-03 — Correct-PIN password recovery is broken

**Evidence:** `api/routes/auth.js:370-418`.

`db` is block-scoped inside the fallback lookup but is referenced later by `saveDatabaseVerified(db, ...)`. On the normal structured-Turso lookup path, `db` is never declared. Even the fallback declaration is out of scope at the write.

**Impact:** users cannot reliably recover accounts with a correct PIN; the route reaches a server error instead of persisting the reset.

**Fix:** fetch/declare the mutable database once in function scope, update the canonical user object, persist atomically, upsert structured user data and test the complete reset/login/token-invalidation lifecycle.

### HIGH-04 — Whole-document merge loses concurrent nested updates

**Evidence:** `api/lib/db.js:158-227`, `api/lib/schema.js:80-109`.

CAS protects the `ps_kv` version, but after a conflict `mergeById()` performs a shallow object merge where the stale local object wins. Arrays inside the same user/post/message—likes, comments, follows, requests, push subscriptions and similar state—are replaced rather than operation-merged.

A deterministic audit probe reproduced the issue: a remote post liked by user A merged with a stale local copy liked by user B produced only B, dropping A.

**Impact:** concurrent likes/comments/follows or edits to the same entity can silently disappear despite successful responses.

**Fix:** make structured tables the sole write source of truth. Model likes, comments, follows and requests as normalized rows with constraints/idempotent operations. Until migration, use mutation-specific merge functions and verify intended nested changes after CAS.

### HIGH-05 — Tier-0 chat/realtime routes bypass all ordinary abuse limits

**Evidence:** `api/lib/omni-engine.js:454-470`, `api/lib/register-middleware.js:79-86`.

Health, readiness, messages read/send/reaction, RTC, SSE and presence are classified Tier 0. Tier 0 performs no token-bucket wait, queue admission or load shedding, and the later global rate limiter explicitly bypasses every critical request. Only auth routes add separate durable limits.

**Impact:** an authenticated account can hammer message reads/writes, RTC signaling, presence and streaming, driving Turso/CPU/push costs or degrading all users. `/api/ready` is unauthenticated, performs a DB round trip and also bypasses ordinary limits.

**Fix:** “critical” should mean priority, not unlimited. Add high but finite per-user/per-IP limits and concurrency caps for chat/RTC/SSE/presence; separately edge-cache or protect readiness probes. Preserve reserved capacity while rejecting abusive callers.

### HIGH-06 — GitHub fallback is pointed at a public repository

**Evidence:** committed `wrangler.toml` points fallback storage at `ajitjaat1011-ui/PRIV-SPACA`, branch `data`, file `db.json`; GitHub reports the repository as public. Production has a GitHub PAT configured.

The file does not currently exist publicly, so no current `db.json` exposure was observed. However, if Turso configuration is removed or fallback mode is activated, the code can create/write the entire database—emails, password/PIN hashes, messages, push subscriptions and social graph—into a public branch.

**Impact:** catastrophic data exposure under a configuration change or fallback activation.

**Fix:** remove database-write fallback completely, or point it at a dedicated private repository with a least-privilege token and encrypted backup format. Add a startup guard that refuses GitHub database persistence when repository visibility is public.

## 5. Medium findings

### MED-01 — Static application shell lacks the API’s security headers

Production `/` returned `X-Frame-Options: SAMEORIGIN`, but no CSP, HSTS, COOP or CORP. The strong `api/lib/security-headers.js` policy applies to Worker/API responses, not the static HTML where script execution matters most. The app stores a seven-day bearer token in `localStorage` and contains many `innerHTML`/inline-handler sites, increasing the impact of any future XSS.

**Fix:** apply security headers to `/*` in `_headers`. Migrate inline scripts/handlers toward external listeners and use CSP hashes/nonces so `script-src 'unsafe-inline'` can be removed. Prefer an HttpOnly/Secure/SameSite session cookie or a short-lived access token plus rotating refresh strategy.

### MED-02 — Deployed Hono version has known advisories

`npm audit --omit=dev` found one direct moderate production vulnerability: Hono `4.12.27` is below the fixed `4.12.34` boundary. The reviewed app does not import Hono’s affected CORS/memo/proxy/language helpers, reducing practical exposure, but the version remains vulnerable and a fix is available.

Full audit: 6 total dependency findings—1 moderate production issue and 5 high dev-tool/transitive issues involving Wrangler/Miniflare/Sharp/Undici/brace-expansion.

**Fix:** update Hono and refresh the lockfile immediately. Upgrade Wrangler/Miniflare under Node 22, then rerun all deterministic and production suites.

### MED-03 — SSE places the seven-day bearer JWT in the URL

**Evidence:** `app.js:4612-4616`.

EventSource connects with `/api/stream?token=<JWT>`. Query tokens can enter edge request logs, analytics and diagnostic tooling.

**Fix:** issue a short-lived, single-purpose SSE token with narrow audience/expiry, or use `fetch()` streaming with the Authorization header. Redact query strings at every logging layer.

### MED-04 — Realtime architecture has high database amplification

Each authenticated SSE connection polls `ps_events` every 1.5 seconds and auto-closes after 24 seconds, causing repeated connection churn. The client simultaneously retains polling backstops, including RTC every 1.5 seconds. At moderate concurrency this creates substantial Turso traffic.

Production secrets for GetStream exist, but the browser does not use the GetStream endpoints/SDK.

**Fix:** choose one durable realtime transport—Cloudflare Durable Objects/WebSockets, Queues plus DO, or fully integrate GetStream. Remove duplicated SSE/database/client polling after cutover.

### MED-05 — Presence and typing can be lost across isolates

Heartbeat/typing writes call whole-database ephemeral persistence, globally throttled per isolate, while immediate fan-out is isolate-local and not persisted. Multiple users on one isolate can have heartbeat writes acknowledged without being stored; users on other isolates can miss non-persisted presence/typing events.

**Fix:** use dedicated TTL rows or a durable realtime coordinator, keyed per user/room, instead of whole-document ephemeral writes.

### MED-06 — Password-recovery design relies on a four-digit PIN

Durable account lockout and subject/IP limits materially reduce brute force, but a four-digit PIN is still weak as the only recovery proof, especially because usernames and currently emails are enumerable to authenticated users.

**Fix:** after repairing recovery, require verified email/passkey recovery, recovery codes or admin-assisted reset. Do not allow PIN-only remote password replacement for higher-risk accounts.

### MED-07 — Link-preview SSRF defense needs resolver-level validation

The route has useful protocol, port, literal private-IP, redirect, timeout and size controls. Remaining gaps include no DNS-resolution validation/pinning and hostname canonicalization edge cases such as trailing dots. Cloudflare’s outbound-network restrictions reduce but do not replace application-layer checks.

**Fix:** canonicalize hostnames, reject trailing-dot local/internal variants, resolve and verify all A/AAAA results before every fetch/redirect where the platform permits, and use an outbound allow/deny proxy if strong SSRF guarantees are required.

### MED-08 — Media upload trusts declared MIME without magic-byte validation

Upload routes validate data-URL MIME, decoded size and an allowlist, but do not verify that bytes match the claimed image/video format. The generic media path allows up to 24 MB before base64 overhead and can consume Worker memory/CPU.

**Fix:** verify magic bytes and dimensions/duration server-side or force Cloudinary transformations; reject malformed/polyglot content; add route-specific upload quotas.

### MED-09 — Username/email uniqueness is application-only

Production currently has zero duplicate username/email indexes, but database indexes are not `UNIQUE`. Concurrent signups/renames can pass the read-then-check race.

**Fix:** add unique constraints/indexes and map constraint conflicts to 409. Plan migration checks before creating them.

## 6. Low findings

### LOW-01 — Source files and owner identifiers remain public

`/app.js` and `/style.css` are intentionally served in production, exposing readable source, historical comments and stable owner account IDs. This is not a secret by itself, but it improves attacker reconnaissance and adds unnecessary deploy weight.

**Fix:** block unminified source assets in production and remove hardcoded owner-ID checks from the client; trust only a server-provided presentation claim.

### LOW-02 — Security suite has a false failure and misses critical auth flows

The suite compares entire wrong-password and unknown-account bodies. Correlation/request IDs are intentionally unique, so JSON equality fails although status and generic messages match. It also lacks passkey, correct-PIN reset, cross-user PII, static-shell headers, concurrency merge and plaintext-at-rest tests.

**Fix:** normalize volatile fields before comparison and add the missing regression cases.

### LOW-03 — Accessibility remains only partially verified

Positive controls include `lang`, alt attributes on static images, reduced-motion rules, selected `focus-visible` rules and several dialog/aria labels. Gaps include many icon-heavy controls, no demonstrated focus traps/restoration for all sheets, extensive inline interactions, and no axe/keyboard/screen-reader browser run.

**Fix:** add Playwright + axe, keyboard-only journeys, focus trapping/restoration, accessible names for every icon button, live-region checks and contrast validation.

### LOW-04 — Initial payload and monolith are heavier than necessary

Approximate compressed production transfer for the shell’s principal resources was about 322 KB before fonts/images. Notable compressed downloads observed: app JS ~86 KB, CSS ~65 KB, auth/React ~51 KB, Lucide ~97 KB, HTML ~13 KB and Motion ~10 KB. Auth React and the full Lucide bundle load even when not needed.

**Fix:** split auth from the authenticated app, tree-shake icons, remove dead historical engines/styles and move route/surface modules out of the 574 KB source monolith.

### LOW-05 — Operational/documentation drift

The code still contains Neon-era comments, an outdated “push no-op” comment, a configured but unused GetStream integration and an old `vercel.json` on the public `data` branch. Package `engines.node >=20` does not reflect the Node 22 requirement of current Wrangler/Miniflare tooling.

**Fix:** clean dead configuration/comments/branches and pin the supported build/deploy runtime.

## 7. Performance and reliability assessment

### Strong

- Cursor paging is indexed and capped.
- Reactions/receipts are hydrated with message pages in one Turso batch.
- Message UI virtualization activates above 50 rows.
- IndexedDB queues provide ordered offline operation draining.
- Image compression, lazy decode, blur placeholders and adaptive rendering are present.
- Circuit breaker, fault domains, timeouts, correlation IDs and readiness checks exist.
- Live health TTFB samples were approximately 51–60 ms during this audit.

### Needs work

- Live readiness samples varied from ~285 ms to ~1.24 s because it performs a remote DB check.
- Full database snapshots are still read/merged for many ordinary routes.
- `/api/feed` is named optimized but still filters/sorts the loaded database snapshot rather than querying `ps_user_feeds`/posts directly.
- Realtime polling amplification and Tier-0 unlimited admission dominate scaling risk.
- Shallow conflict merge invalidates the current “concurrency-safe” claim for nested state.
- No browser performance trace, Core Web Vitals, memory profile or multi-user soak/load test was available.

## 8. PWA/offline assessment

## 9. UX/product assessment

Feature breadth is excellent: social feed, stories, chat, reactions, receipts, offline queue, presence, typing, calls, gestures, PWA install and rich media are integrated. The main UX risk is not feature absence but assurance: touch arbitration, story/media physics, variable-height retention, focus management and service-worker updates require real-device browser testing.

Do not market all conversations as encrypted. Only explicitly enabled Secret Chat messages use client-side encryption; ordinary chats are server-readable. Secret Chat uses unauthenticated server-distributed static ECDH keys, no identity verification/safety numbers, no forward secrecy and weak multi-device/key-rotation behavior. It is useful confidentiality against passive database reading but is not Signal-grade E2EE.

## 13. Release recommendation

**Current production can remain online for a small trusted beta only if biometric/passkey 2FA is disabled or urgently fixed.** Do not onboard sensitive communities or make strong security/E2EE claims until CRIT-01 and HIGH-01 through HIGH-03 are resolved. P0 work should be treated as the next release, ahead of additional visual or feature expansion.
